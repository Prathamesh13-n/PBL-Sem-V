DAY 9 - REQUEST STATUS LIFECYCLE
===========================================================

WHAT WE BUILT
--------------
Files updated:
1. app/schemas.py
   - Added reviewed_by field to ResourceRequestOut
   - Added RejectRequest schema (optional reason field)

2. app/routes_requests.py
   - Added ALLOWED_TRANSITIONS map defining exactly which status changes
     are legal:
       pending      -> approved, rejected
       approved     -> provisioning
       provisioning -> provisioned, failed
       rejected, provisioned, failed -> (terminal states, no further moves)
   - Added transition_status() helper that enforces this map, raising a
     400 error on any invalid transition attempt
   - Added three admin-only endpoints:
       PATCH /requests/{id}/approve
       PATCH /requests/{id}/reject
       PATCH /requests/{id}/start-provisioning

WHY IT MATTERS
---------------
This is the core business logic of the whole portal - it guarantees a
request can never skip steps (e.g. jump straight from "pending" to
"provisioned") or go backwards illegally (e.g. get approved again after
being rejected). Every transition is validated server-side, not just
assumed to be correct.

VERIFICATION PERFORMED
------------------------
[x] PATCH .../approve on a pending request -> 200, status "approved"
[x] PATCH .../approve on that SAME request again -> 400 Bad Request
    (blocked - already approved, correctly rejected)
[x] PATCH .../start-provisioning -> 200, status "provisioning"
[x] PATCH .../reject on a different request -> 200, status "rejected"
[x] PATCH .../approve on that rejected request -> 400 Bad Request
    (rejected is terminal - correctly blocked)

Result: All transition rules enforced correctly, no invalid state change
was ever allowed through.

HOW TO RUN (two terminals needed, both at once)
---------------------------------------------------
Terminal 1 (backend):
  cd backend
  venv\Scripts\activate
  uvicorn app.main:app --reload
  -> runs on http://127.0.0.1:8000

Terminal 2 (frontend):
  cd frontend
  npm install      (only needed the first time)
  npm run dev
  -> runs on http://localhost:5173

PROBLEMS ENCOUNTERED AND FIXED
---------------------------------
1. Nested folder issue (frontend\frontend) from zip extraction, same
   pattern as earlier days - fixed by working from the correct outer
   folder.

2. CORS (Cross-Origin) blocking - the backend's terminal log showed
   successful "200 OK" responses to /health, but the browser still
   displayed "Could not reach backend." This is because browsers block
   JavaScript from reading cross-origin responses (frontend on port 5173,
   backend on port 8000) unless the server explicitly allows it.
   Fix: Added CORSMiddleware to app/main.py, explicitly allowing
   http://localhost:5173 as a permitted origin. This is a standard,
   expected step in any frontend/backend project running on separate
   ports - not a mistake, just a necessary configuration piece.
