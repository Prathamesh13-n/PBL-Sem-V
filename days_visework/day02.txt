```
│   ┌───────────────────────┐        ┌───────────────────────┐     │
│   │   User Web Browser    │        │   Admin Web Browser    │    │
│   └───────────┬───────────┘        └───────────┬───────────┘     │
└───────────────│────────────────────────────────│─────────────────┘
                 │                                │

        ┌──────────────────────────────────────────────┐

```

**Layer summary:**
- **Frontend (React):** presentation only; talks to backend exclusively via REST, never touches AWS/Terraform directly.
- **Backend (FastAPI):** single source of truth for auth, business rules, and orchestration. Owns the state machine for request status.
- **Innovation Module:** pure rule-based logic (no external calls) — recommendation, cost, security score — runs synchronously when a request is created.
- **Terraform Orchestrator:** a thin backend service that generates a `.tfvars` file per request and shells out to `terraform apply`, then parses `terraform output` / state file to capture instance ID and IP.
- **Database:** system of record for users, requests, and deployment metadata — independent of whether AWS/Terraform succeeds or fails.
- **AWS:** the only external system; accessed exclusively through Terraform, never via direct SDK calls from the backend (keeps provisioning auditable and reproducible).

## 2. User Workflow

```
 [Register/Login]
        │
        ▼
 [User Dashboard]
   - Total / Pending / Approved / Rejected / Provisioned counts
        │
        ▼
 [New Resource Request]
   - Fill form: workload level, OS, region, storage, purpose
        │
        ▼
 [System auto-generates on submit]
   - Recommended instance type
   - Estimated monthly cost
   - Security score
        │
        ▼
 [User reviews & confirms submission]
        │
        ▼
 [Request status = Pending]
        │
        ▼
 [User waits / checks Request History page]
        │
        ▼
 [Status updates automatically: Approved → Provisioning → Provisioned]
        │                                   (or → Rejected / Failed)
        ▼
 [Provisioned request shows EC2 Instance ID + IP on dashboard]
```

```

   - List of all requests (all users), filterable by status
        │
        ▼
 [Select a Pending request]
        │
        ▼

        │
        ▼
   ┌────────────┴────────────┐
   ▼                         ▼
[Approve]                 [Reject]
   │                         │
   ▼                         ▼
Status → Approved      Status → Rejected (End)
   │
   ▼
Backend triggers Terraform Orchestrator
   │
   ▼
Status → Provisioning (visible to admin & user in real time)
   │
   ▼

   │
   ▼
Admin can view deployment result (instance ID, IP, or failure reason)
```

## 4. AWS + Terraform Workflow

```
 [Request Approved by Admin]
        │
        ▼
 [Backend: Terraform Orchestrator]
   1. Generate request-specific *.tfvars
      (instance_type, os_ami, region, storage_gb, tags)
        │
        ▼
   2. Run: terraform init (once per environment)
        │
        ▼
   3. Run: terraform plan -var-file=request_<id>.tfvars
        │
        ▼
   4. Run: terraform apply -auto-approve -var-file=request_<id>.tfvars
        │
   ┌────┴────┐
   ▼         ▼
Success    Failure (e.g. quota, invalid AMI, permission error)
   │         │
   ▼         ▼
5. Parse   5. Capture stderr/log
terraform     │
output        ▼
   │       Status → Failed
   ▼       (store error message for admin/user)
Extract:
 - instance_id
 - public_ip
 - state = "provisioned"
   │
   ▼
Store in Deployments table, linked to ResourceRequest
   │
   ▼
Status → Provisioned
   │
   ▼
Reflected on User Dashboard + Admin Dashboard
```

**Key design decisions locked in for Day 2:**
- Terraform runs **per-request** using a generated `.tfvars` file, not one shared config — keeps requests isolated and auditable.
- Backend never calls the AWS SDK directly; **all AWS changes flow through Terraform** so state files remain the single source of truth for what's deployed.
- Status transitions are **one-directional** (no going back from Provisioned to Pending) — simplifies the state machine and dashboard logic.
- Terraform execution is **synchronous from the backend's point of view but async from the user's** — the API returns immediately after triggering, and the frontend polls status.
